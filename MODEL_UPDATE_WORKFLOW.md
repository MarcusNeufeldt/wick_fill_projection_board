# Manual Wick Data and Model Update

The dashboard has two different update cycles:

1. **Live source refresh** appends completed Binance candles every minute and recalculates active pins with the currently installed evidence and models.
2. **Manual learning refresh** rebuilds the historical evidence and numerical models so newly resolved wicks become training and route-selection examples.

The live refresh does not retrain anything. Run the manual update periodically when enough new fills have accumulated; weekly or on demand is sufficient for the current research workflow.

## Commands

Preview every stage without writing files:

```powershell
cd F:\explore\candle_projection_algo
.venv\Scripts\python.exe .\wick_update.py update --dry-run
```

Run the complete update:

```powershell
cd F:\explore\candle_projection_algo
.venv\Scripts\python.exe .\wick_update.py update
```

`--skip-refresh` is available only for a deliberate rebuild from the existing fixed local candle snapshots.

## What the command updates

| Layer | Action | Effect in the dashboard |
| --- | --- | --- |
| Binance sources | Catch up all five assets at 1m and 5m | Current prices, signal status and active-pin state become current |
| Completed-route evidence | Rebuild the pooled five-asset 5m library and each asset's isolated 1m library | Newly completed paths become eligible for V1/adaptive and soft-state historical matching |
| Derived 15m V1 routes | Regenerated by the pooled 5m builder for compatibility | Existing 15m V1 projections remain available; no 15m model is trained |
| Runtime caches | Rebuild the pooled 5m cache and all five 1m caches | The new libraries remain fast enough for interactive use |
| Rust history kernels | Compile the tracked release crate; trace/write 1m/5m clean routes and scan prospective outcomes with strict parity checks | Route and all-outcome rebuilding scale across the five assets without changing dashboard schemas |
| All-outcome observations | Rebuild resolved, unresolved and right-censored entry histories | Recently filled wicks receive observed waiting-time and adverse-movement labels |
| Numerical risk models | Retrain one pooled five-asset model for 1m and one for 5m | The Risk from current price card can learn from the refreshed outcome data |

The command does **not** retrain these experimental or fallback layers:

- V3 neural route experts. Each age expert still needs a separate chronological route-quality experiment and explicit promotion decision.
- The older completed-fill-only V2a fallback. Its files are preserved when the pooled route library is replaced.

Consequently, new completed paths immediately enter the historical V1/soft-state route population, while a supported Adaptive Normal route can still come from the previously validated V3 expert. The dashboard's Observed state panel shows which selector supplied Normal.

## Promotion rule

The new completed-route libraries and outcome dataset are deterministic rebuilds from the refreshed source candles. They are validated for required files and non-empty populations before promotion.

The numerical risk models have an additional chronological gate. A candidate must improve adverse-risk error and waiting-time error over the frozen soft-state baseline without regressing either probability score. A passing candidate replaces the installed timeframe artifact; a failing candidate is discarded and the currently installed model remains active.

This gate compares the newly trained numerical challenger with the frozen baseline on the refreshed chronological evaluation split. It does not claim that every weekly retrain is better than every previously installed model on a permanently untouched test period.

The frozen 5m Forecast Architecture V1 has a stricter contract. An update run
trains it under a unique candidate architecture ID and saves it under the
installed `5m/candidates/` directory. It never changes `5m/active.json` or the
immutable artifact currently named there. The trainer also refuses a direct
attempt to overwrite that active frozen artifact. Candidate activation requires
a separate explicit decision after the prospective window; it is not part of
`wick_update.py update`.

## Resource expectations

Treat a complete run as an overnight maintenance job:

- The route builders are CPU-, RAM- and disk-I/O-intensive, especially for five years of 1m candles.
- The updater requires Cargo/Rust. It locates Cargo from `CARGO`, `PATH`, or the installed Windows stable toolchain, compiles the release kernel once, and requests Rust explicitly for route and outcome stages. A missing binary or parity failure aborts the update before promotion.
- Assets are processed sequentially, so all five 1m libraries are not held in memory simultaneously.
- Each library is staged one at a time, limiting temporary disk use to roughly one replacement library plus working overhead. Keep several gigabytes free.
- The default workflow does not retrain V3 and therefore does not use CUDA or the GPU.
- Keep the computer connected to power and prevent Windows from sleeping until the command finishes.

On Windows, stop the dashboard before a full update. Its memory-mapped library
files can prevent an atomic directory promotion. Restart it after the updater
finishes. A models-only resume does not replace route-library directories.

## Interruption and recovery

Every route library is built in `data/.wick_update_staging/<run-id>/` and validated before its installed directory is swapped. An interruption during a library build therefore leaves that library's previous installed version intact.

The overall workflow is sequential. If it is interrupted after earlier stages were promoted, those completed stages remain updated while later stages remain old. Raw-source refresh also happens before the library rebuilds. Rerun the same command to converge every layer on the latest source snapshot; source refresh and rebuilds are repeatable.

When every route library and `data/prospective_entry_outcomes_v1` has already
been promoted and only model training failed, validate and reuse that installed
dataset instead of repeating the route work:

```powershell
.venv\Scripts\python.exe .\wick_update.py update --models-only
```

This mode retrains/gates the 1m and 5m numerical models and writes a new frozen
5m candidate, but does not refresh candles, rebuild routes/caches, or change the
active frozen manifest.

A normal failure or keyboard interruption records the result in the run manifest. A force-killed process can leave an ignored staging directory and a manifest whose last state is `running`; neither is used by the dashboard. Verify that no updater process remains before deleting such a staging directory.

## Evidence and reload behavior

Each real run writes an ignored manifest to:

```text
data/wick_update_runs/<UTC-run-id>.json
```

It records stage commands, durations, failures, completed-episode deltas, outcome counts and model-promotion decisions. Generated training reports remain under `data/prospective_entry_models/<timeframe>/training_report.json`, while installed numerical models default to `%LOCALAPPDATA%\candle_projection_algo\prospective_entry_models\<timeframe>\model.joblib`. Forecast V1 candidates and their reports are stored under `%LOCALAPPDATA%\candle_projection_algo\prospective_entry_models\5m\candidates\`; the active frozen version remains identified only by `5m\active.json`.

The dashboard detects changed source generations, library timestamps, cache fingerprints and model modification times. A service restart is normally unnecessary; the next applicable request reloads the changed artifact.

## Verification

The update orchestrator itself can be checked without starting the expensive rebuild:

```powershell
.venv\Scripts\python.exe -m py_compile .\wick_update.py .\test_wick_update.py
.venv\Scripts\python.exe -m unittest -v test_wick_update.py
.venv\Scripts\python.exe .\wick_update.py update --dry-run
```
